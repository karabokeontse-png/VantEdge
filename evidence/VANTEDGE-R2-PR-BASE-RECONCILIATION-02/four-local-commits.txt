body:
Phase A of the CED authority/integrity directive - Requirements Forwarding
Repair (completion).

CycleViewModel.runAnalysis() accepted requiredSkills, preferredSkills and
educationRequired but omitted all three when calling runPipeline(), so the
authoritative values extracted by JobInputScreen never reached the analysis
pipeline. Downstream, JobRequirementAdapter saw structuredRequiredCount=0
and silently substituted DESCRIPTION_FALLBACK, scoring against mined
description text instead of the extracted requirements.

Three changes:
  - runPipeline() now accepts the three requirement parameters.
  - Both requirement-consuming branches forward them: runAnalysisOnly()
    (NEW_APPLICATION / QUICK_ANALYSIS) and runFullPipeline() (QUICK_GENERATE).
    Previously only QUICK_GENERATE passed anything, and it read the mutable
    ViewModel fields rather than the invocation values.
  - runAnalysis() forwards its received parameters into runPipeline().

runGenerationFromCycle() (IMPROVE) is intentionally untouched - it reuses
cycle.compatibility by design.

Eliminates the parameter-versus-field divergence: no analysis branch now
reads savedRequiredSkills/savedPreferredSkills/savedEducationRequired.
Those fields are write-once from JobInputScreen and are never reset anywhere
in CycleViewModel, so relying on them was also a staleness hazard. Removing
them as an input for this path closes that hazard.

Removes the now-false TD-RELIABILITY-002 warning that documented this
defect.

Verified: :app:compileDebugKotlin BUILD SUCCESSFUL, 0 errors.
Runtime telemetry deferred to CoGo.
